# iSpatialGym task definition and evaluation decisions

Status: agreed cross-task design, updated 2026-09-06 (evaluator implemented;
see "Implementation status"); "Instance artifacts" and "Task spec (customs
list)" updated 2026-09-15 for the v2 sampling rebuild (`instance_sampling_spec.md`).

This document records the shared design for the seven iSpatialGym tasks. Detailed
task semantics, tolerances, observations, action spaces, and oracle policies will
be reviewed separately for each task.

See `task_bddl_formats.md` for the proposed concrete BDDL templates.

## Scope and source of truth

- The benchmark uses the R1Pro robot.
- Demonstrations will be generated by scripted simulation oracles with privileged
  state access.
- `Behavior-1K/` is the authoritative reference for BDDL parsing, task loading,
  scene loading, object states, and evaluation behavior.
- iSpatialGym should extend the BEHAVIOR pipeline narrowly rather than replace it
  or weaken BEHAVIOR's validation globally.
- Existing unrelated experimental implementations are not design references.

## Instance artifacts

Each benchmark instance consists of:

1. A BDDL problem describing symbolic objects, initial relations, and logical
   goals — grounded by `ground_isg` from the subtask's **iddl** (role-level
   definition, `ispatialgym/assets/iddl/`) and the **icl** (candidate list,
   `ispatialgym/assets/icl/`); one problem per category combination, named by
   its alias.
2. A versioned TRO record containing the materialized scene state and numeric
   evaluation targets.
3. A task spec entry (iSpatialGym's version of the BEHAVIOR task-custom list)
   describing how instances of that problem are generated: per-scene model
   whitelists / blacklists, bindings of the scene roles, generation parameters
   (group sizes and draw mode, spawn scales, chosen joints, counts, tolerances)
   and the constraints learned from earlier instances.
4. An **oracle sidecar** (`<instance_id>.oracle.json`) with everything the
   scripted demonstration policy needs (stances, grasps, contacts, waypoints,
   paths); the evaluator never reads it and the public release may omit it.
   It carries facts only: the action sequence is the oracle's per-subtask
   program (`oracle_primitives_design.md` §3.7), and the only writer of
   evaluation targets on the demo side is the `run_isg` executor's epilogue
   (goal-pose override after the settled check, oracle doc §3.8).

BDDL describes **what** must hold. The TRO stores concrete values required to
instantiate and evaluate that statement. The task spec describes how those
values are produced. The sidecar describes how the oracle reaches them.

Task specs are generation-time input only. Runtime loading must not resample a
model or layout from them: the exact selected scene, models, and poses must
already be materialized in the generated instance.

BDDL files must follow BEHAVIOR's discoverable, contiguous naming convention:
`problem0.bddl`, `problem1.bddl`, and so on.

## Task spec (customs list)

BEHAVIOR's `task_custom_lists.json` has one entry per activity with a
`room_types` list and exactly one scene key holding `whitelist`/`blacklist`.
Only the innermost shape matters to the code: the sampler passes
`whitelist`/`blacklist` unchanged to `BehaviorTask(sampling_whitelist=...)`,
where `BDDLSampler` looks them up by synset as
`{synset: {category: {model: null | [bbox]}}}`. The single-activity,
single-scene, `room_types`, and `inroom`-based binding conventions belong to the
challenge scripts, which iSpatialGym cannot reuse (definition `0` hard-coded,
one scene, no `inroom`).

iSpatialGym therefore keeps one file (`task_custom_lists.json` in its own
metadata directory, never BEHAVIOR's) with a different entry structure
(schema and example in `instance_sampling_spec.md` §2.3):

- **Key by alias** (`inter_object_relation_satisfaction-nextto-spatula-soup_ladle-breakfast_table`):
  one entry per grounded BDDL problem. The definition id is recorded inside
  (`definition_id`, from `activity_definitions/<activity>/problems.json`).
- **`roles`**: the roles of the grounded problem (from the icl `roles/candidates.csv`, the
  iddl declares none) with their grounded category, a `sampleable` flag
  (`true` = spawned from the whitelist per template, `false` = a scene role
  bound per scene), the iddl `require` entries (`grasps: <pipeline>`,
  `contacts`, `handle`) the loader and oracle read the grasp pipeline from, the
  representative model, and the per-role draw parameters: `scale` (per-model
  spawn scale, alignment targets) and `joint` / `handle_key` (articulation).
- **`scenes`**: one block per candidate scene (all seven unless the icl bounds
  the scene): task rooms, `bindings` of the scene roles to scene object names
  (or `{"category": [...]}` / `{"room": ...}`), and the **per-scene
  `whitelist` / `blacklist`** of models per role and category. Whitelists start
  as the full icl pool minus the models rejected by the iddl `:require` filters
  (`missing_grasps:<pipeline>`, `missing_contacts`, `missing_handle`); a model
  that fails its representative test moves to the blacklist with the rejection
  reason. Scene-dependent objects (supports, walls, scene articulated objects,
  big partners) are listed per scene.
- **`generation`**: scene-independent draw parameters — template and instance
  counts, tolerances, `groups.<role>` for every group role (`size`: integer or
  `[min, max]`; `draw`: `unique` or `same_model` — blocks `{4, same_model}`,
  distractors `{[1, 3], unique}`, obstacles `{1, unique}`), and the
  camera-relocalization `path_buckets` (`[{"max_m": 3, "n": 10}, ...]`,
  half-open geodesic ranges, overridable on the `multiply_isg` command line).
  `ground_isg` seeds it from the existing entry of the alias or from the
  per-subtask defaults (`ispatialgym/sampling/generation_defaults.py`, the
  numbers of `instance_sampling_spec.md`); the samplers hold no defaults of
  their own.
- **`constraints`**: typed, scoped records appended by every successful
  sampling run (`stance`, `grasp_set`, `joint_set`, `placement`, `scale`,
  `band_ref`, `contacts`, `blacklist`) with `hard` and `source` fields. Soft
  records are priors that narrow the draws of later runs; hard records reject.
  This is how "robot placed x from the edge of the table" and every other
  initialization rule that a successful instance confirmed is expressed for
  reuse, next to the BEHAVIOR predicate sampling the samplers still use.

Generation runs per scene: bind the scene roles, spawn models from the whitelist,
run the initialization rules of `instance_sampling_spec.md`, settle, validate
(`:init` true, goal false, goal feasible, every pose of the expanded oracle
program IK- and collision-feasible — the program check of
`instance_sampling_spec.md` §3.5), derive rooms, and write the TRO with `object_bindings`,
`load_room_instances`, the spec file hash (`task_spec_sha256`) and the sidecar.

## Room-independent BDDL

`inroom` is optional for iSpatialGym BDDL. iSpatialGym should have its own
verification profile that skips BEHAVIOR's requirement that every scene object
be transitively placed from exactly one `inroom` condition. The shared BEHAVIOR
validator must retain its existing behavior.

Removing `inroom` from BDDL does not remove the scene loader's need to know which
geometry to load. Each TRO must therefore store:

- The exact scene model and floor.
- Concrete room-instance IDs, not only room types.
- The resolved set of rooms and other geometry required by the instance.
- Exact object bindings and models.
- The robot's initial state and location.

The resolved load scope must be stored during generation. Inferring it later
from only the robot position is insufficient because the camera may observe
adjacent geometry and the robot may reach across room boundaries.

## Deterministic loading

Generation may use a recorded seed, but loading a materialized instance must not
perform random sampling.

The authoritative environment construction order is:

1. Load variables.
2. Load the scene.
3. Load objects.
4. Load robots.
5. Load the task.
6. Load external sensors.

BEHAVIOR's evaluator subsequently overlays TRO object state and robot poses,
runs a fixed settling sequence, updates the initial snapshot, and resets from
that snapshot.

iSpatialGym requires these extensions:

- Pre-read TRO scene/load-scope metadata before environment construction because
  partial-room selection is needed when the scene is loaded.
- Restore full required R1Pro state, not only its root pose. Grasped-object tasks
  require arm and gripper configuration plus deterministic grasp restoration.
- Apply TRO-backed predicate configuration after task scope has been resolved.
- Run a fixed, deterministic settling sequence.
- Revalidate BDDL initial conditions and all target references after restoration.
- Fail on missing objects, links, sensors, frames, targets, or tolerances instead
  of silently falling back.

The current BEHAVIOR TRO format does not preserve all robot joint, controller,
and grasp information needed by Object Scaling and Mental Rotation, so the
iSpatialGym TRO schema must extend it.

Caveat for scripted settling code (generation, probes): OmniGibson caches
kinematic predicates (`ontop`, `touching`, `inside`, ...) per object pair and,
in `KinematicsMixin._cache_is_valid`, treats an object that PhysX has put to
sleep as unchanged without comparing its pose. A predicate evaluated while an
object is still moving (e.g. by `PotentialReward` at `env.reset()`), then not
re-evaluated while the object comes to rest and falls asleep, keeps returning
the stale value. Episode evaluation is unaffected because the goal is
re-evaluated every `env.step` while objects move; `load_tro_instance` is
unaffected because `scene.reset()` re-places (wakes) the objects before the
next evaluation. Code that steps physics without evaluating goals must wake or
re-place objects before querying kinematic predicates.

## TRO responsibilities

The exact schema remains to be implemented, but a TRO must be able to represent
the following information:

The concrete proposal in `task_bddl_formats.md` keeps standard BEHAVIOR object
state and `robot_poses` keys at the top level and places the fields below inside
a reserved top-level `ispatialgym` metadata object.

```yaml
schema_version: isg-tro-v1
activity: camera_relocalization
instance_id: camera_relocalization-0001
generation_seed: 1234
task_family: camera_relocalization
task_variant: null

scene:
  model: ...
  floor: ...
  load_room_instances: [...]

robot:
  model: r1pro
  state: ...
  grasp_state: ...

objects:
  object_instance:
    model: ...
    state: ...

pose_targets:
  object_instance:
    link: null
    frame: world
    position: [...]
    orientation: [...]
```

The final schema should use BEHAVIOR-compatible serialized states where possible
and reserve a versioned metadata section for iSpatialGym-specific targets,

## `pose_reached`

`pose_reached` remains a unary BDDL predicate:

```lisp
(pose_reached ?object_instance)
```

There is no separate `camera_goal` BDDL symbol. The corresponding TRO entry
provides the target pose, evaluated entity link or sensor, frame, and tolerances.
`pose_reached` must not appear in `:init` merely to configure a target.

The common v1 semantics are:

- The TRO target selects what is compared through `position_metric`
  (`"full"`, `"depth"`, or `null`) and `orientation_metric` (`"full"` or
  `null`). Camera Relocalization compares the full camera pose, Object Scaling
  only the depth along the head-camera optical axis, Mental Rotation and World
  Alignment only the orientation. Every enabled metric has its own tolerance.
- Use the world frame for all task pose targets, except the depth metric,
  whose frame is the head-camera sensor.
- Report position error in meters and orientation error in radians separately.
  The orientation error is frame independent (a common frame change cancels in
  the angular distance), so a world-frame and a table-frame orientation goal
  coincide for a static table.
- BEHAVIOR's other restricted-axis modes (`z`, `xy`, `yaw`) remain available on
  `PoseReached` but are not part of the iSpatialGym TRO schema.
- A `pose_reached` (or `layout_reached`) atom in the goal gates success; the
  same atom in the problem's `(:measure ...)` section is configured and its
  errors are reported identically, but it never gates. Every TRO target must
  correspond to one of the two, so the BDDL alone states what is evaluated.

The TRO `link` field controls which pose is evaluated:

- A non-null value is resolved strictly against the entity's sensor keys first
  and then its link names.
- An unknown value is an error.
- `link: null` uses the entity's normal pose API. This is the root pose for an
  ordinary object and the base-footprint pose for a holonomic robot. For R1Pro,
  the latter is `base_link`.
- Camera Relocalization stores the exact camera sensor key rather than relying
  on an agent-specific hard-coded link.

The loader must call `PoseReached.set_goal()` from TRO metadata. A pose target
without both required tolerances is invalid; otherwise the current state can
skip an unconstrained error component.

## Configuration Matching

The task previously called Block Design is now the **Configuration Matching**
benchmark family (`task_family: configuration_matching`). It contains three
explicitly labeled variants:

1. `block_design`: reproduce a configuration of interchangeable blocks.
2. `articulation`: move an articulated object to the pictured configuration
   (closed to open, or open to closed).
3. `attachment`: attach one object to another in the pictured
   configuration.

All variants live in one activity directory,
`activity_definitions/configuration_matching/problemN.bddl`, and each problem
names its variant with an `(:alias ...)` section. Two problems share the
`articulation` alias, one per direction. The alias is recorded as
`task_variant`, and results are reported both for the aggregate task and per
alias.

Because BEHAVIOR's sampler hard-codes definition `0` and keys task-custom lists
by activity, iSpatialGym generation must take the definition id and read the
per-problem task spec described above.

### Groups

BDDL gains a `(:groups members - group_name)` section. Pointwise predicates on
a group expand to a conjunction over members; a negated pointwise literal
expands to "no member satisfies it"; `layout_reached` and `pose_reached` on a
group are aggregate predicates evaluated once with a shared member-to-slot
assignment. Group symbols are nonphysical scope entities.

### Shared predicate roles

Across all variants, `layout_reached` is the relative or internal
configuration and `pose_reached` is the absolute world placement:

| Variant | `layout_reached` | `pose_reached` |
| --- | --- | --- |
| block design | pairwise relative poses between blocks | every block at its assigned slot |
| articulation | joint positions (link poses relative to the base link) | root pose |
| attachment | child pose in the parent frame | both objects at their slots |

### Block-design variant

`layout_reached(blocks_group)` is defined as relations between the blocks: each
TRO relation stores one slot's pose in another slot's frame, and the evaluator
checks the same relative pose between the blocks assigned to those slots.
Relations are invariant to where the arrangement sits, so a correct design
displaced on the table still satisfies `layout_reached`. Binary success is
`ontop`, `layout_reached` and release; the absolute placement
(`(:measure (pose_reached ?blocks_group.n.01_1))` against `target_slots`) is
reported as the block-design pose error but does not gate success.

One shared, one-to-one block-to-slot assignment is computed per evaluation step,
consumed by both predicates, and logged. Its cost is the total relation error
(`assignment.cost = "layout"`, invariant to a rigid motion of the arrangement;
ties broken by member name then slot id); `"slot_position"` is available for
groups without relations. `orientation_equivalences` handles block symmetry on
both ends of every relation. `pose_settled(blocks_group)` expands per block and
does not depend on the assignment.

### Articulation variant

`layout_reached(articulated_object)` is the object's internal configuration:
every non-fixed joint has a target position and tolerance in the TRO, and all
must hold. Because joint positions exactly parametrize the moving links' poses
relative to the base link, this covers any number of independently moving links
with a fixed part-to-target mapping. Binary success is the `open` guard,
`layout_reached` and release. A movable articulated object may add a root pose
target (`pose_reached` with `link: null`); fixed-base assets do not need one.

`open` is kept as a semantic guard in both directions (`open` goal for opening,
`(not (open ...))` goal for closing). BEHAVIOR's `Open` only checks that a
relevant joint crossed a small threshold, so it cannot express the exact pictured
configuration alone.

### Attachment variant

The goal combines the directional `attached(child, parent)` relation with a
fixed-assignment group containing both objects: `layout_reached` checks the
child's pose in the parent frame (gating), while the group's `target_slots`
record both world poses for error reporting only.
`attached` verifies a real BEHAVIOR attachment joint; the TRO names the exact
male/female attachment-link pair because BEHAVIOR serializes only the parent
object.

## Disembedding initial occlusion

The previous `non_overlapping` requirement is removed. The target object should
instead be externally occluded by other candidate objects in a configured
fraction of generated instances while remaining detectably visible.

This is a dataset-generation and initial-state validation constraint, not a BDDL
goal. A probability applies to an instance distribution and therefore does not
belong in a deterministic BDDL problem. Generation configuration should define:

- The probability of sampling an occluded instance.
- A minimum external-occlusion ratio that distinguishes the occluded bucket.
- A maximum external-occlusion ratio below 1.
- A minimum visible target area in pixels.
- The designated camera sensor key and image configuration.

For a target-only amodal/reference silhouette area `A` and its visible area `V`
in the complete scene:

```text
external_occlusion_ratio = 1 - V / A
```

The target-only reference should use the same camera while hiding the other
candidate objects. This excludes the target's self-occlusion. The generator must
also keep the target projection fully within a configured image margin so that
out-of-frame cropping is not counted as occlusion.

Each TRO records the realized ratio, visible area, occluding object IDs, and
camera key. The loader recomputes and validates them after deterministic
settling, with a small tolerance for rendering variation.

A shallow source tray is preferable to a box if a container is used: it bounds
the clutter layout while keeping the candidates reachable and reducing
container-wall occlusion. It does not replace explicit occlusion sampling.
Container-induced occlusion should be separately bounded so the desired
occlusion comes primarily from candidate objects.

The source container must be different from the destination tray; otherwise the
target would satisfy the placement goal at episode start. Candidate objects can
be initialized `ontop` the source tray, while the selected target's goal remains
`ontop` the destination tray. Whether every instance uses a source tray remains
a task-specific decision.

## Tray semantics

Destination-tray membership uses `ontop` only:

- The selected target must satisfy `(ontop target tray)`.
- Distractors must satisfy `(not (ontop distractor tray))`.
- `inside` is not part of benchmark success or exclusion.

This avoids model-dependent `Inside` behavior for shallow trays and follows
BEHAVIOR tray-task conventions.

## `pose_settled`

`PoseSettled(agent)` monitors the whole articulated R1Pro state: root motion,
joint motion, and configuration drift. It is not limited to the base or to the
link selected by `pose_reached`.

Required settlement entities are:

| Task | `pose_settled` entities |
| --- | --- |
| Camera Relocalization | agent |
| Object Scaling | manipulated object, agent |
| Mental Rotation | manipulated object, agent |
| Disembedding | selected object, agent |
| Configuration Matching — block design | every block in the group, agent |
| Configuration Matching — articulation | articulated object, agent |
| Configuration Matching — attachment | both attached objects, agent |
| World Alignment — table surface | manipulated object, agent |
| World Alignment — world vertical | hinged object, agent |
| World Alignment — world horizontal | hinged object, agent |
| Inter-object Relation Satisfaction | both manipulated objects, agent |

Each `pose_settled` atom should be an explicit top-level BDDL goal. A group form
is expanded to one atom per physical member during compilation.

Define:

- `G(t)`: all non-`pose_settled` goals are true at step `t` (binary success).
- `S(t)`: all required `pose_settled` goals are true at step `t`.
- Binary success: `G(t)` reached at any step of the episode.
- Settled success: `G(t) AND S(t)`.

`ISpatialGymTask` takes two flags:

```yaml
task:
  require_pose_settled: false        # official success = settled success when true
  terminate_on_binary_success: false # end the episode at the first G(t) instead of the first G AND S
```

- Binary success and settled success are always both reported, whatever the
  flags. `require_pose_settled` only decides which one `task.success` (the
  BEHAVIOR-compatible official success) means.
- By default the episode continues after the first `G(t)` until the first
  `G(t) AND S(t)` so that the settle latency can be measured; a timeout after
  `G` was reached leaves `success = true` (binary mode) with latency `-1`.

```text
t_goal = first t where G(t)
t_settled = first t >= t_goal where G(t) AND S(t)
latency_steps = t_settled - t_goal
latency_seconds = latency_steps * sim_step_dt
```

The timer remains anchored at the first `G(t)` if a non-settlement goal
temporarily becomes false before final settled success. The final success step
must still satisfy all goals simultaneously.

The BDDL conditions determine which entities must settle. The flag controls
whether those conditions gate official success; evaluation code must not infer
an entity list from task names.

BEHAVIOR's per-entity `pose_settled` instrumentation (`info["done"]["pose_settled"]`)
is kept; the task-level `t_settled`, latency and termination live in
`ISpatialGymTask`.

## Observation timing: BEHAVIOR convention (decided 2026-09-06)

iSpatialGym adopts BEHAVIOR's observation pipeline unchanged, for demos, goal
images and evaluation alike.

Facts the decision rests on (measured on the `ispatialgym` env, R1Pro, 30 Hz
control, `n_render_iterations=1`):

- `env.step(i)` runs the physics for step `i` and dispatches one render. The
  render products readable after the step (RGB, depth, `camera_params`
  including `cameraViewTransform`) show the scene as it was after step `i-2`
  (two-frame readback latency of the asynchronous renderer; occasionally one
  frame right after a teleport). Proprioception, joint states and every object
  pose are physics-synced (state `i`). Three renders per step would make the
  frames current, at 1.7-2x the per-step cost with three 1080x1080 cameras.
- BEHAVIOR has used `env.step(..., n_render_iterations=1)` in both the 2025
  and 2026 challenge evaluators and renders its training observations by
  replaying recorded states through the same call (`DataPlaybackWrapper`), so
  its policies were trained and evaluated with this latency, and its
  `_preprocess_obs` builds `cam_rel_poses` from the camera pose *of the frame*
  (`cameraViewTransform`) expressed in the *current* base frame, which is the
  correct pairing for unprojecting the frame's depth into the robot's current
  base frame (`process_fused_point_cloud`).

Decision:

1. **Control and rendering**: `env.step(action, n_render_iterations=1)`. The
   evaluation profile (`isg-v1`) pins `n_render_iterations: 1` next to the
   camera configuration (sensor key `robot_r1:zed_link:Camera:0`, 1080x1080,
   40 mm horizontal aperture, as in `omnigibson/eval/r1pro.yaml`).
   `ispatialgym.eval.episode.run_episode` exposes the same parameter with this
   default.
2. **Policy input**: exactly BEHAVIOR's `Evaluator._preprocess_obs` semantics:
   flattened observation dict, proprio from the current physics state, images
   two frames old, `cam_rel_poses` = per-frame camera extrinsics in the current
   base frame, plus `task_id`. The image/proprio asynchrony is accepted: it is
   a fixed, learnable latency of the same order as real camera pipelines, and
   matching BEHAVIOR keeps iSpatialGym compatible with BEHAVIOR-challenge
   policies and baselines. `cam_rel_poses` is an extrinsics signal, not
   proprioception, and must not be reinterpreted as the robot's current camera
   pose.
3. **Demos**: oracles act on privileged physics state, but the recorded
   observations must come from `env.step` with `n_render_iterations=1` (live,
   or by replaying recorded states with `DataPlaybackWrapper` at the same
   value), so demo frames carry the same latency as evaluation frames.
4. **Goal images**: captured with the robot and every task object stationary
   at the goal configuration, after at least three renders (use 10, as the
   playback wrapper does for its initial frame) so the frame is current; the
   RGB frame is stored with the physics-synced sensor prim pose as
   `goal_observation.camera_pose_world`, using the same camera configuration as
   evaluation. For a static scene the latency is irrelevant and image and pose
   describe the same state.
5. **Evaluation**: every predicate (`pose_reached` on objects, the robot base
   or the head-camera sensor, `layout_reached`, `ontop`, `grasped`,
   `pose_settled`, ...) is judged on physics-synced state at the current step.
   Camera Relocalization therefore uses the sensor prim pose, which is the pose
   of the frame dispatched at that step (visible to the policy two steps
   later), never the render-side transform. The reported `first_success_step`
   thus precedes the first policy observation of the matching image by the
   render latency; settled success (>= 10 stationary steps) makes the two
   coincide.

Changing the convention later (e.g. `n_render_iterations=3` for current
frames) is a profile change that must be applied to demos, goal images and
evaluation together; it never affects the evaluator's success or error
metrics.

## Common metrics and logging

`ISpatialGymTask` writes `info["done"]["ispatialgym"]` every step and
`ispatialgym.eval.episode.summarize_episode` turns the final one into the
episode result:

- `success` (official), `binary_success`, `first_success_step`.
- `settled_success`, `first_settled_success_step`, `settle_latency_steps`,
  `settle_latency_seconds`.
- `position_error` / `orientation_error`: the maximum over the pose targets
  (scalar targets and group members), taken at the first binary success or, if
  it never happened, at the terminal step. `layout_position_error` /
  `layout_orientation_error`: the same over the layout targets (group relations;
  prismatic / revolute joints of articulated objects).
- `errors`: the per-target detail behind those maxima (`pose_errors`,
  `layout_errors`, each with the metric labels, `within_tolerance` and whether
  the atom is `gating`); `errors_at_termination` for the last step.
- `group_assignments`: the shared member-to-slot assignment per group.
- `conditions`: every goal atom with its BDDL text, kind (`binary` /
  `pose_settled`) and truth value, for diagnosing failures; `measured`: the
  non-gating `:measure` atoms with their within-tolerance status.

Meters and radians remain separate. No normalized or mixed-unit aggregate error
is included in v1.

## Agreed task-level constraints

These are cross-task decisions only; each task still needs a dedicated review.

- Camera Relocalization evaluates the actual head-camera sensor pose (full
  position and orientation).
- Object Scaling and Mental Rotation retain `grasped` plus a partial pose goal:
  depth along the head-camera axis for Object Scaling, world-frame orientation
  for Mental Rotation. Their initial grasp must be restorable from the instance.
- Disembedding samples controlled candidate-object occlusion of the target and
  requires the selected object `ontop` the destination tray and released; the
  exact target pose is measured (`pose_targets` on the object, not on the
  agent) but does not gate success.
- Configuration Matching contains block-design, articulation, and
  attachment variants. Every variant gates success on `layout_reached` for the
  relative or internal configuration together with `open`/`(not (open ...))` or
  `attached` as the semantic guard; absolute placement (`target_slots`) is
  measured only.
- Alignment (activity `alignment`, previously World Alignment / Rod and Frame)
  has three variants. Axial (previously table surface): the object starts and
  stays `ontop` the table while reaching its target orientation. World vertical: an object (e.g. a painting) hangs on a wall
  through a revolute joint at its center of mass and must be rotated to the
  straight orientation; the hinge is restored from a TRO constraint record rather
  than expressed with `attached`, because BEHAVIOR attachment aligns meta links
  and would not pivot at the center of mass. World horizontal: the same wall
  hinge, but the object is an elongated wall item with one clear horizontal
  direction (a towel bar, a hook rail, a shelf, a wide sign) that starts tilted
  and must be rotated back to level; because "horizontal" is undirected, models
  that look the same upside down list the 180-degree flip about the wall normal
  in `orientation_equivalences`.
- Inter-object Relation Satisfaction, previously called Relation Satisfaction,
  gates success on the intended spatial-relation predicate and release; the
  exact pictured poses are measured only. `open` remains excluded from this
  task because articulation now belongs to Configuration Matching. It has
  seven subtasks (ontop / under × small-scale / large-scale, inside, nextto,
  touching); the small-scale `under` puts the manipulated target on the
  partner, so its goal is `(under ?partner ?target)`; `inside` does not
  evaluate the target's orientation.
- Configuration Matching's articulation variant is split into large-scale
  (scene objects, opened primarily by base / trunk motion) and small-scale
  (spawned objects on a support, handle arm + brace arm), each in an open and a
  close direction.

The concrete BDDL for each variant is in `task_bddl_formats.md`.

## Implementation status

Implemented (see "Implementation status" in `task_bddl_formats.md` for the
file-level map):

- The `ispatialgym` BDDL domain without `inroom`, parser support for `:alias`
  and `:groups`, group expansion, and compilation into the stock `bddl` trees.
- Versioned TRO evaluation metadata (`isg-tro-v1`) with validation, and
  TRO-to-`PoseReached.set_goal()` / `LayoutReached.set_goal()` / group-target
  configuration.
- `layout_reached` for groups (relative poses) and articulated objects (joint
  targets), and group-aware `pose_reached` with a shared assignment.
- Flag-controlled settled/binary success, task-level latency, per-target error
  reporting (`ISpatialGymTask`), and a TRO loader that overlays object states
  and the robot root pose / joint positions, settles, and snapshots.

Remaining gaps (instance restoration and generation):

- TRO pre-reading for partial-room configuration before environment
  construction.
- Grasp, attachment-link, hinge-constraint and controller-target restoration
  (recreated after every reset).
- The v2 generation pipeline (`ground_isg` / `sample_isg` / `multiply_isg`)
  and the oracle sidecar (`instance_sampling_spec.md`).
- Controlled initial-occlusion generation, recording, and reload validation.
- Initial-condition revalidation after restoration is available
  (`compiled_task.check_initial_conditions`) but not enforced by the loader.
